# System Tray Presence Implementation Plan

> **Design doc:** `docs/superpowers/specs/2026-08-07-system-tray-design.md` — read this first for the full rationale behind two things this plan resolves: why Task 3 (hide-to-tray) was dropped entirely rather than softened, and why a missing tray icon during development is very likely a GNOME environment issue, not a code bug.

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking. Depends on the app icon (already built) and plan 25's real `TitleBar` close button.

**Goal:** A system tray icon (using the icon already built) with a quick-access context menu, so bringing the app's window to front or starting a new recording doesn't require hunting for it among other windows.

**Resolved decision (2026-08-07):** the tray is a **pure convenience**, not a window-lifecycle change. The title bar's close button keeps its existing, deliberate, recently-built behavior — it quits the app, full stop. This plan originally proposed changing close to "hide to tray instead of quit," but that directly conflicted with a real, dated design decision (`docs/superpowers/specs/2026-08-06-titlebar-close-button-design.md`) explicitly scoping *"no tray icon, no hide instead of quit behavior."* Reversing a decision that was just deliberately made wasn't worth it for a convenience feature — so this plan no longer touches close-button semantics at all. The original Task 3 (changing that behavior) is dropped entirely, not deferred.

**What this means in practice:** since the window can never be hidden without the app quitting entirely, the tray's "Show" action isn't un-hiding anything — it's bringing an already-running, already-visible (per `alwaysOnTop`) window to focus, useful if it's drifted behind something, off-screen, or on a different virtual desktop.

> **Pre-flight review (2026-08-08):** this plan was written against an earlier/aspirational snapshot of the codebase, and one design-doc claim points at an asset that was never actually delivered into the repo. Verified corrections below, each also inlined as a `> **Deviation:**` note at its exact step:
> 1. **`src-tauri/src/main.rs` is a 12-line stub** (sets `GDK_BACKEND=x11` under Wayland, then calls `meeting_notes_lib::run()` — no `.setup()` at all). The real `.setup(|app| { ... })` closure lives in `src-tauri/src/lib.rs` (confirmed at line 52). Every "modify `main.rs`'s setup closure" instruction below means `lib.rs` — this is the identical gap plan 29 (mic-activity-detection) hit and documented the same way.
> 2. **`tray-icon` is not part of `tauri`'s default feature set**, confirmed against the real crate source (`~/.cargo/registry/.../tauri-2.11.5/Cargo.toml`): `default = ["wry", "compression", "common-controls-v6", "dynamic-acl", "x11", "dbus"]` — no `tray-icon`. The repo's `src-tauri/Cargo.toml` currently has `tauri = { version = "2", features = [] }`. Task 1 Step 1's framing ("confirm `default-features = false` isn't set") is the wrong check — `default-features` is already `true` (unset), but `tray-icon` still isn't in that default list, so it must be added explicitly to the `features` array regardless.
> 3. **No `app-icon-1024.png` (or any 1024px) source exists anywhere in this repo**, despite the design spec's claim (§4) that one was "built earlier in this conversation" — that conversation and any resulting asset were never committed. `src-tauri/icons/` only has the standard Tauri-generated set: `32x32.png`, `64x64.png`, `128x128.png`, `128x128@2x.png`, `icon.png`, `icon.icns`, `icon.ico`, plus Windows `Square*Logo.png` variants. Task 1 Steps 2-3 use a real existing file (`icons/32x32.png` is closest to actual tray render size) rather than a nonexistent source, and skip building a new "simplified flat variant" — there's no design asset to base one on, and inventing new icon art is out of scope for this implementation pass. If the reused icon reads muddy at tray size once actually visible on a real desktop, that's a follow-up, not a blocker here.
> 4. **This implementation sandbox is headless (no display server at all)** — `echo $XDG_CURRENT_DESKTOP` here returns `ubuntu:GNOME` (confirming the plan's GNOME concern is real for whoever runs this on a real desktop), but manual verification (Task 1 Step 5, Task 2 Step 3) cannot be performed in this sandbox regardless of GNOME extensions, same gap as prior plans' "no live Tauri verification" limitation. Verify via `cargo build`/`cargo check` only; report the manual-verification gap explicitly rather than claiming it was done.
> 5. **`TitleBar.tsx`'s close button (`src/components/TitleBar.tsx:41-45`) calls `getCurrentWindow().close()`, and `lib.rs` has no `WindowEvent::CloseRequested`/close-intercepting handler** (its one `on_window_event` handler only reacts to `Resized`) — so Tauri's default behavior (quit on last window close) applies uninterrupted. This *confirms* the plan/spec's "close always quits, tray never changes that" assumption is correct against the real code; no deviation needed here, just verification.
> 6. **"Plan 21's hotkey ignore-if-busy reasoning" and "plan 25's real `TitleBar` close button" are phantom citations** — no plan files numbered 21 or 25 exist in `docs/superpowers/plans/`, and no `global_shortcut`/`GlobalShortcut` code exists anywhere in this repo (the identical phantom-plan-21 issue plan 29 hit). Not a blocker: the actual titlebar close-button behavior these citations lean on is independently confirmed real via point 5 above, and Task 2 Step 2's own inline `if (widgetState === "idle")` check is already a complete, self-contained "ignore if busy" guard that doesn't need an external precedent to follow.
> 7. **`RecorderWidget` currently exposes no external "start recording" trigger** — confirmed against `RecorderWidgetProps` (`src/components/RecorderWidget.tsx:26-38`), which only has `resumeMeeting` (a value prop watched by a `useEffect`, lines 102-105) and `onStateChange`. The real internal start handler is `handleStart` (line 252), only ever called from an internal button's `onClick`. Task 2 Step 2's "verify against the real component" note undersells this — there is no existing mechanism to verify against; a new one must be added. Corrected approach at that step mirrors the established `resumeMeeting` pattern (a value prop bumped by the parent, watched by a new effect) rather than the plan's placeholder comment.

- [ ] **Step 4: Check GNOME tray support FIRST, before assuming the code is broken**

If developing on stock Ubuntu (GNOME is the default desktop since 17.10), the tray icon **will not appear anywhere** without a GNOME Shell extension — this isn't a bug to debug, it's a deliberate GNOME decision to drop native `StatusNotifierItem`/AppIndicator support, and it affects every Electron/Tauri app with a tray icon, not just this one. Check which desktop environment is actually running:

```bash
echo $XDG_CURRENT_DESKTOP
```

If it says `GNOME` (or `ubuntu:GNOME`), install one of these before testing further:
- **"AppIndicator and KStatusNotifierItem Support"** from extensions.gnome.org, or
- **"Tray Icons: Reloaded"** (same site)

Then log out and back in (GNOME Shell extensions typically need a Shell restart, which a simple app restart doesn't trigger). KDE Plasma, XFCE, Cinnamon, and MATE all support tray icons natively with no extension needed — this step only applies to GNOME.

### Task 2: Tray context menu (Show/Hide, New Recording, Quit)

**Files:**

- Modify: `src/App.tsx`

- [ ] **Step 1: Build the menu and wire click handlers**

> **Deviation:** this replaces Task 1 Step 3's simpler `TrayIconBuilder` call in `lib.rs`'s setup closure — don't add a second tray icon, extend the one already registered in Task 1 with the menu/event-handler chain below.

```rust
// src-tauri/src/lib.rs (additions, replacing/extending Task 1's
// TrayIconBuilder call in the same setup closure)
use tauri::menu::{Menu, MenuItem};
use tauri::tray::TrayIconEvent;
use tauri::Manager;

let show_item = MenuItem::with_id(app, "show", "Show", true, None::<&str>)?;
let new_recording_item = MenuItem::with_id(app, "new_recording", "New Recording", true, None::<&str>)?;
let quit_item = MenuItem::with_id(app, "quit", "Quit", true, None::<&str>)?;
let tray_menu = Menu::with_items(app, &[&show_item, &new_recording_item, &quit_item])?;

TrayIconBuilder::new()
    .icon(tray_icon)
    .tooltip("Meeting Notes")
    .menu(&tray_menu)
    .on_menu_event(move |app, event| match event.id.as_ref() {
        "show" => {
            if let Some(window) = app.get_webview_window("main") {
                let _ = window.show();
                let _ = window.set_focus();
            }
        }
        "new_recording" => {
            if let Some(window) = app.get_webview_window("main") {
                let _ = window.show();
                let _ = window.set_focus();
                let _ = app.emit("tray-new-recording", ());
            }
        }
        "quit" => app.exit(0),
        _ => {}
    })
    .build(app)?;
```

- [ ] **Step 2: Frontend listens for "New Recording" from the tray and triggers a real start**

> **Deviation:** `RecorderWidget` currently exposes no external "start recording" trigger — see pre-flight note #7. Read `src/components/RecorderWidget.tsx` (its `RecorderWidgetProps`, the `resumeMeeting` prop + its watching `useEffect` around lines 26-38 and 102-105, and `handleStart` at line 252) and `src/App.tsx` (where `<RecorderWidget resumeMeeting={resumeMeeting} onStateChange={handleWidgetStateChange} />` is rendered) before writing this — the corrected approach below mirrors the existing `resumeMeeting` pattern rather than the plan's original placeholder comment. Also use the StrictMode-safe `cancelled`-guard `listen()` pattern already established elsewhere in `App.tsx` (e.g. the mic-activity-detection listener), not the plan's original bare `unlistenPromise.then(...)`.
>
> In `RecorderWidget.tsx`: add a new optional prop, e.g. `triggerNewRecording?: number`, to `RecorderWidgetProps`. Add a new `useEffect` watching it (mirroring the `resumeMeeting` effect's shape) that calls `handleStart()` when the prop changes to a new value and `state === "idle"` — guard on a ref for the previous value (like `resumeMeeting`'s effect does) so it only fires on an actual change, not on every render.
>
> In `App.tsx`: add `const [trayNewRecordingSignal, setTrayNewRecordingSignal] = useState(0);`, a `listen("tray-new-recording", ...)` effect (cancelled-guard pattern) that does `setTrayNewRecordingSignal((n) => n + 1)`, and pass `triggerNewRecording={trayNewRecordingSignal}` into the `<RecorderWidget>` element. This keeps the "is a recording already in progress" guard (`state === "idle"`) inside `RecorderWidget` next to `handleStart` itself, rather than duplicating widget-state knowledge in `App.tsx`.

```tsx
// src/App.tsx — illustrative shape only, adapt to the real listen()
// idiom already used in this file (cancelled-guard) and the real
// state/prop names once you've read the files above:
const [trayNewRecordingSignal, setTrayNewRecordingSignal] = useState(0);

useEffect(() => {
  let cancelled = false;
  let unlisten: (() => void) | undefined;
  (async () => {
    const stop = await listen("tray-new-recording", () => {
      if (cancelled) return;
      setTrayNewRecordingSignal((n) => n + 1);
    });
    if (cancelled) { stop(); return; }
    unlisten = stop;
  })();
  return () => { cancelled = true; unlisten?.(); };
}, []);

// <RecorderWidget resumeMeeting={resumeMeeting} onStateChange={handleWidgetStateChange} triggerNewRecording={trayNewRecordingSignal} />
```
